# 06 · 动态码兑换与位置签到

> 结论来自两处：服务器真实 cookie 实测（2026-11-16，changjiang 域）+ course_helper 源码 +
> `com.xuetangx.ykt` 1.3.6 协议分析报告字段级对齐。所有请求都已在 `/opt/yktsign/loc.py` 实现。

## 一、动态二维码：只能拿真码兑换，签名不可构造

二维码 URL 形如
`https://changjiang.yuketang.cn/v/course/lesson/<lessonId>/checkin?c=<ticket>&t=<ts>&s=<sig>&v=2`

服务端用自有密钥算 `s`，客户端没有任何签名逻辑（协议分析报告确认 App 请求无签名头）。
实测三种输入到 `POST /api/v3/app/scan`（**必须** `x-client: app` + Android UA，桌面头直接 400）：

| 输入 | 返回 |
|---|---|
| `junk` | `{"code":50033,"msg":"QR_CODE_NOT_FOUND"}` |
| 无 c/t/s 的 checkin URL | `{"code":51201,"msg":"动态二维码不合规范"}` |
| c/t/s 构造（s=x） | `{"code":51202,"msg":"动态二维码签名验证失败"}` |

所以离线爆破 `s`、平移 `t`、拼 URL 全部无解。唯一可用路线是 **兑换法**：

```
POST /api/v3/app/scan   {"url": "<二维码整条 URL>"}     # 移动端头
  → {"code":0,"data":{"value":"1821000000000000001"}}   # value 就是 lessonId
POST /api/v3/lesson/checkin {"source":21,"lessonId":"<上一步>","joinIfNotIn":true}
```

**产品含义**：不需要本人在场，只需一张二维码截图/一段 URL 文本（群里转发、同学拍照都行），
服务器就能对**每个托管账号**分别签到 —— 比"真码图转发、每人各自扫"强一个档位。

代码：`loc.app_scan(raw, acct)` → `loc.scan_and_checkin(raw, accts, source=21)`
接口：`POST /api/app/scan-exchange {url}`（自动取该用户全部已绑定账号）
前端：概览 → 扫码签到 → 粘贴 URL → 「兑换并签到（全部账号）」

## 二、位置签到：端点与字段已确认

```
GET  /api/v3/lesson/location-checkin/eligibility      Bearer <Set-Auth>
POST /api/v3/lesson/location-checkin/preview          {"lat","lng","lessonId"}  Bearer <Set-Auth>
POST /api/v3/lesson/location-checkin/submit           {"lat","lng","lessonId","source":54,"address"}
```

- `eligibility` 实测返回：`{needLocationSignIn, signed, mode, checkInTime, address}`；
  位置签到开启时还会带 `centerLat/centerLng/radiusM/serverTime/isLate/wouldBeLate/lateAfterMs/startMs/endMs/session`。
- `preview` 实测返回：`{sessionActive, reason, inRange, message}`，开启时带 `distanceMeters/radiusMeters`。
- `submit` 在未开启位置签到的课上返回 `51210 请使用位置签到完成考勤` —— 说明**报文体已通过校验**，
  只是这节课本来不该走这条路。
- 提交体没有时间字段，服务端自己算距离和迟到；客户端只有展示型 gate。

**坐标必须是 GCJ-02**。华南沿海一带 WGS-84 直塞会偏 400~600 m，必判范围外。
`loc.wgs2gcj()` / `loc.gcj2wgs()` 已实现（实测 22.2565,113.5429 → 22.253544,113.54801）。

接口：`POST /api/app/geo/eligibility {acct, lessonId?}`、`POST /api/app/geo {acct, lessonId, lat, lng, address?, gcj?}`
（后者一次跑完 eligibility → preview → submit，返回每一步原始响应）。
前端：任务 tab → 位置签到 → 「探测本课位置规则」「预检并提交」。

## 三、调度器行为

任务开启「位置签到」且填了 lat/lng 时，每一轮：

1. `do_checkin(source=5)` 常规签到（拿 Set-Auth）；
2. `geo_flow()`：eligibility → preview → submit(source=54, GCJ-02)；
3. 结果合并进同一条 `runs` 记录，备注里区分三种情况：
   `+ 位置签到 [lat,lng]` / `+ 位置签到未通过(code=…)` / `+ 本节未开位置签到`。

## 回放链路修复（2026-11-16 19:0x，现场）

现象：扫码页「回放完成」但未拿到 token。

取证：
- `captures.jsonl` 三条 19:06:35–19:06:40 的回放，steps 只有一条 `{"tag":"GET-url","status":401}` —— 桌面端直接 GET 那个签到 URL 被雨课堂拒绝（URL 里的 `c/t/s` 是 **App 端票据**，不是桌面会话能直接消费的）。
- 同一时刻调度器通配任务（task 3）在 19:07:06 拿到 `{"code":0,...,"lessonToken":"…"}`，`lesson_auth.json` 落盘 280 B JWT，payload = `{l:1821000000000000002,s:1794826542,c:26000001,u:3214,d:85389,i:57486095,p:3,r:["105"],iat,exp}`，`logs/learn` 该课节 `attend_status=true` —— **签到实际成功**，只是页面没显示 token。

根因：老 `/api/replay` 只走桌面 GET 回放，没有 App 端兑换通道。

修复（`web.py`）：
```
res = svcclient.replay(raw, acct)
if not res.get("ok"):
    ex = svcclient.scan_exchange(raw, [acct])   # POST /api/v3/app/scan，x-client: app + Android UA
    one = ex["results"][0]
    res = {"ok": one["ok"], "via": "app-scan", "lessonId": ..., "code": ..., "hint": ...}
```
并回传 `tokenHead`（前 28 位）+ `tokenLen`，前端 `render()` 显示 `token … (280 B)` 与「通道: App 端兑换」。

复测（用 19:06:35 那条旧码）：steps 变为 `[GET-url 405, POST-ticket 200 auth=true]`，`ok=true`，lessonId 正确 —— App 兑换通道生效，且旧码在有效期内仍可兑换。

坑：`/api/replay` 需要 `X-Key` 请求头（`key.txt` 内的 key），不带返回 `{"error":"bad key"}`；curl 自测容易漏。
## 六、决定性发现：source=46 通用入口不需要码（2026-11-16 19:26 实测）

同一节课（中国近现代史纲要，classroom 26000001，lessonId `1821000000000000002`）：

| 入口 | 结果 |
|---|---|

## 七、位置签到全自动（2026-11-16，人不到也能签）

服务端只在 submit 时校验 **坐标与签到中心点的距离**，不校验设备、不校验 Wi-Fi、不校验到场证明。
所以「人不到」的实现方式就是：读 eligibility 下发的中心点与半径，自己算一个圈内坐标提交。
对手站 CourseGod 的「签到位置 + 地图选点」是同一个原理，只是它让人手动点地图。

### 7.1 三端点（已实测，全部需要 lesson 级 Set-Auth）

| 方法 | 端点 | 作用 |
|---|---|---|
| GET | `/api/v3/lesson/location-checkin/eligibility` | 是否开启、是否已签、中心点、半径、时间窗、地址 |
| POST | `/api/v3/lesson/location-checkin/preview` | 预检 `{lat,lng,lessonId}` → `{sessionActive,inRange,message}` |
| POST | `/api/v3/lesson/location-checkin/submit` | 提交 `{lat,lng,lessonId,source:54,address}` |

返回码：`0` 成功 · `51210` 本节课未开启位置签到（报文体合法的最好证明）· `51211` 不在范围 · `401` lesson 级 Set-Auth 过期。

> **关键细节：Set-Auth 只有 30 秒有效期**（JWT `exp - iat = 30`）。所以每次自动签到都要先现取一次：
> `loc._grab_auth()` 优先用缓存，缓存过期就打一次 `POST /api/v3/lesson/checkin {source:46}` 顺手收新的 `Set-Auth`。
> 这也解释了线上跑 `loc_eligibility()` 直接返回 `401` 的现象。

### 7.2 自动坐标算法（`loc.auto_point`）

```python
d  = max(3.0, min(radius * frac, radius - 1.0))      # frac 默认 0.45，留边界余量
dlat = d * cos(bearing) / 111320
dlng = d * sin(bearing) / (111320 * cos(lat))
```

- `eligibility` 里的 `centerLat/centerLng` **本身就是 GCJ-02**（服务端坐标系），所以偏移后直接提交，`gcj=False`，**不要**再转一次。
- 用户自己填的经纬度来自浏览器 `navigator.geolocation`（WGS-84），那条路径仍然 `gcj=True` 自动转换。
- 实测换算：`22.2565,113.5429`（WGS-84）→ `22.253544,113.54801`（GCJ-02）。

### 7.3 降级重试链

`frac` 依次取 `0.45 → 0.25 → 0.1 → 0.02`，每档先 `preview`：

- `sessionActive=false` → 立即放弃（`stage=window_closed`，窗口没开，重试无意义）
- `inRange=false` → 换更靠近中心的一档继续
- `inRange=true` → `submit(source=54)`

实测（半径 120 m）：`0.45` 出 `22.253964,113.548272`(54 m)、`0.25` 出 30 m、`0.1` 出 12 m、`0.02` 出 3 m。

### 7.4 `geo_auto` 的 stage 语义

| stage | 含义 | 是否算成功 |
|---|---|---|
| `already` | 该课节已签到 | 是 |
| `no_rule` | 本节没开位置签到，通用入口签到就够 | 是 |
| `submitted` | 位置签到提交成功 | 是 |
| `window_closed` | 位置签到未开始/已失效 | 否 |
| `no_center` | 开了位置签到但没下发中心点 | 否 |
| `rejected` | 服务端拒绝（带 code） | 否 |
| `out_of_range` | 四档坐标都判不在范围 | 否 |
| `error` | eligibility 读不到（含 401 重取一次仍失败） | 否 |

### 7.5 调度器行为（`app.py`）

